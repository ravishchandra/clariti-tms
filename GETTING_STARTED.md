# Getting started

A 5-minute walkthrough that runs ClaritiTMS end-to-end with zero API keys. By the end you'll have ingested strings, run them through the translation pipeline, and seen the canonical state-machine output. Real LLM providers are a one-line config flip after.

This guide assumes you've cloned the repo and have **Docker** + **Python 3.12+** installed.

---

## 1. Bring up Postgres + apply migrations (~2 min)

```bash
# Postgres with pgvector
docker compose up -d postgres

# Python env
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

# Schema
cd infra && alembic upgrade head && cd ..
```

If Docker can't bind 5432, edit `infra/docker-compose.yml` to map a different host port and update your `DATABASE_URL`.

---

## 2. Run the demo (~30 sec)

```bash
loc demo --locale fr-FR
```

This creates a fresh `demo-<timestamp>` project under org `demo`, ingests 5 sample strings, registers a **mock LLM provider** (no API keys needed), and walks the strings through the production translation pipeline. You'll see a table like:

```
┏━━━━━━━━━━━━━━━━━━━━━━━━┳━━━━━━━━━━━━━━━━━━┳━━━━━━━━━━━━━━━━━━━━━━━━┳━━━━━━━━━━━━━━┓
┃ key                    ┃ source           ┃ fr-FR                  ┃ status       ┃
┡━━━━━━━━━━━━━━━━━━━━━━━━╇━━━━━━━━━━━━━━━━━━╇━━━━━━━━━━━━━━━━━━━━━━━━╇━━━━━━━━━━━━━━┩
│ checkout.button.pay    │ Pay {{amount}}   │ [fr-FR] Pay {{amount}} │ needs_review │
│ errors.network         │ Could not reach… │ [fr-FR] Could not reach│ needs_review │
│ onboarding.welcome     │ Welcome to Clari…│ [fr-FR] Welcome to Cl… │ needs_review │
│ settings.account.label │ Account          │ [fr-FR] Account        │ needs_review │
│ settings.title         │ Settings         │ [fr-FR] Settings       │ needs_review │
└────────────────────────┴──────────────────┴────────────────────────┴──────────────┘
```

What just happened, technically:

- The CLI created `Organization → Project → Repository → LocaleConfig` rows.
- A temp source file with five i18next strings was parsed and upserted as `Key` rows.
- Draft `Translation` rows were created for each key+locale pair (Phase 1).
- `assemble_batches()` grouped them into a single `TranslationBatch` keyed by `(component, screen, locale)` (Phase 1).
- A mock `LLMProvider` was registered with the runtime LLM registry — it implements the same Protocol as `AnthropicProvider`, `OpenAIProvider`, etc., but returns canned translations prefixed with `[locale]` so the round-trip is visible.
- `translate_batch()` ran the full pipeline: TM neighbor lookup → glossary injection → pre-processing → mock LLM call → post-processing → validators → back-translation QA (skipped for the mock) → risk-class routing → final write through `apply_transition()` on the canonical `draft → mt_proposed → {needs_review, approved}` path (Phase 2).
- The risk-class heuristic flagged every demo string as `standard` (the default), which forces `needs_review` per the human-review workflow at `docs/06`. That's why no string auto-approved — it's working correctly.

Run with `--locale de-DE` or `--locale es-ES` for a different target locale. Each run creates its own timestamped project, so previous demos are preserved.

## 3. Swap in a real LLM provider (~1 min)

```bash
export ANTHROPIC_API_KEY=sk-ant-...   # or OPENAI_API_KEY
```

Then translate a real source file you control:

```bash
loc ingest-file path/to/locales/en/common.json --repo my-web
loc translate --project <project-slug> --locale fr-FR
loc status --project <project-slug>
```

The provider chain (primary → retry → fallback) is documented in `docs/05-llm-translation-pipeline.md:52`. By default it's Anthropic → OpenAI → Ollama. Configure overrides in `tms.yml` (generated by `loc init`).

---

## 4. Wire up your own repo (~2 min)

Run `loc init` inside the repository whose strings you want translated:

```bash
cd ~/code/my-app
loc init
```

It prompts for the repo name, platform (`ios`/`android`/`web`/`backend`), file format (`ios-strings`, `i18next`, `android-xml`, etc.), source file path, and target locales. The generated `tms.yml` is gitignore-safe — secrets aren't stored there, just config.

Then:

```bash
loc ingest-file <your-source-file> --repo <name>
loc translate --project <project-slug> --locale fr-FR
loc pull --project <project-slug> --locale fr-FR
```

`pull` fetches approved translations back into the locale-specific file in your repo.

## 5. Open the API directly (optional)

```bash
uvicorn app.main:app --reload --port 8000
```

- OpenAPI docs: `http://localhost:8000/api/v1/openapi.json`
- Mint an API key: `loc api-key create --name dev` (prints the key once — save it)
- Then: `curl -H 'X-API-Key: <key>' http://localhost:8000/api/v1/organizations`

The full REST surface is auto-generated by FastAPI from the schemas in `app/api/v1/schemas/`. The TypeScript SDK (`@clariti-tms/sdk`) and Python SDK (`clariti-tms`) generate from that OpenAPI spec via `make sdks`.

## Troubleshooting

**`asyncpg.exceptions.InvalidCatalogNameError: database "tms" does not exist`**

Postgres is up but the database hasn't been created. `docker exec infra-postgres-1 createdb -U tms tms`, then re-run `alembic upgrade head`.

**`RuntimeError: SECRET_KEY is required when DEBUG=False`**

Either set `DEBUG=true` for local dev (the demo command does this implicitly when you set it inline) or set a real `SECRET_KEY` of 32+ chars. See `.env.example`.

**`FERNET_KEY not set` warning**

Generate one once with `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` and put it in `.env`. Without it, encrypted columns (webhook secrets, Contentful tokens) won't survive a process restart in dev — fine for the demo, not fine for any real use.

**Demo shows `needs_review` instead of `approved` for every string**

Working as intended. The default risk-class heuristic flags everything as `standard`, which always routes to review. To see auto-approval, you'd need to give a string an `auto_publish` risk class (e.g., add it to a glossary or use it in a context the heuristic recognizes as low-risk).

**`loc translate` fails with "Locale not bootstrapped"**

Per `docs/06:109`, new locales need a 50-string native-speaker review before they go live. Use `loc bootstrap-sample --locale fr-FR` to export the sample, then mark the locale bootstrapped in the DB or web UI once a native speaker has reviewed it. The demo command bypasses this by setting `is_bootstrapped=True` on its demo locale.
