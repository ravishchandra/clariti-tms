# 07 — Excel Round-Trip

Bulk export to XLSX, edit offline, bulk import back. Many reviewers (especially external LSPs and finance-team validators) prefer Excel to any web UI. This becomes the *primary* review interface for some users.

## Why this is high-priority

- LSPs (Language Service Providers) charge less when handed Excel/XLIFF than when asked to log into a custom tool.
- Compliance reviewers in regulated domains (fintech) often want to redline in Excel and email it back.
- Bulk operations are faster in Excel than in any web grid we'd build.

The format is **fixed and versioned**. We do not support arbitrary user-modified columns.

## Export format

Filename convention: `{project-slug}_{locale}_{YYYY-MM-DD}_{status-filter}.xlsx`
Example: `clariti-web_fr-FR_2026-05-16_needs-review.xlsx`

### Workbook structure
- **Tab 1+: one tab per locale being exported.** Tab name = locale (e.g., `fr-FR`, `de-DE`).
- **Last tab: `_meta`** — hidden in the UI but readable. Contains export metadata for re-import validation.

### Locale tab columns (in this exact order — locked)

| # | Column | Type | Editable | Notes |
|---|---|---|---|---|
| 1 | `key` | string | **Locked** | Identity. Changing this breaks re-import. |
| 2 | `source_text` | string | **Locked** | en-US text, for reference. |
| 3 | `description` | string | Locked | What this string is for. |
| 4 | `component` | string | Locked | e.g., `CheckoutButton`. |
| 5 | `screen` | string | Locked | e.g., `checkout`. |
| 6 | `max_length` | int | Locked | Character cap. |
| 7 | `placeholders` | string | Locked | Comma-separated, e.g., `userName, amount`. |
| 8 | `risk_class` | string | Locked | `auto_publish` / `standard` / `high_risk` / `human_only`. |
| 9 | `current_translation` | string | Locked | What's currently in DB. |
| 10 | `mt_suggestion` | string | Locked | Raw MT output. Same as current_translation if no edit yet. |
| 11 | `status` | string | Locked | DB status (informational). |
| 12 | **`reviewer_action`** | dropdown | **Editable** | `yes` / `no` / `edit` / `needs_more_context`. Validated dropdown. |
| 13 | **`edited_translation`** | string | **Editable** | Fill only if `reviewer_action = edit`. |
| 14 | **`notes`** | string | **Editable** | Free text. |
| 15 | `_internal_id` | UUID | **Hidden, locked** | Maps to `translations.id`. Critical for re-import. |

### Formatting rules

- **Frozen header row** (row 1).
- **Locked columns**: 1–11, 15. Protected via sheet protection.
- **Editable columns**: 12, 13, 14. Unlocked cells inside a protected sheet.
- **Column 12 (`reviewer_action`)**: data validation dropdown with the four allowed values. Reject any other input.
- **Column 6 (`max_length`)**: integer formatting; blank if no limit.
- **All translation text columns**: text format (prevent Excel from auto-converting numeric-looking strings).
- **Color coding by current `status`**:
  - Yellow background: `needs_review`
  - Light blue: `mt_proposed`
  - Light green: `approved`
  - Light red: `rejected`
  - Orange: `needs_more_context`
- **Column widths**: source_text ~50ch, current_translation ~50ch, others auto-fit.

```
export_hash            | sha256 of (project_id + export_timestamp + sorted row ids)

```

The `export_hash` is what lets us detect "this file was tampered with structurally" on import.

## Import flow

```
1. User uploads .xlsx via web UI or CLI (`loc import file.xlsx`)
2. System reads _meta tab
3. Validate:
   a. schema_version matches a supported version (v1 currently)
   b. project_id matches the project being imported to
   c. all locale tabs exist as declared
4. Validate all rows (placeholders, length, glossary, ICU, language)
5. Produce dry-run summary
6. Show preview to user. User confirms or cancels.
7. On confirm: write changes in a single transaction
8. Persist import_job row with applied_changes snapshot
9. Set rollback_expires_at = now() + 24h
10. Return success with import_job_id (for rollback)
```

### Conflict detection

Between export and import, the source DB may have changed. We check:

```python
def detect_conflicts(import_job):
    conflicts = []
    for row in import_job.rows:
        current_translation = db.fetch_one(
            "SELECT source_hash_at_translation, value, status, updated_at "
            "FROM translations t JOIN keys k ON t.key_id = k.id "
            "WHERE t.id = $1", row.internal_id
        )
        # Has the source text changed since the export?
        if current_translation.source_hash != row.source_hash_at_export:
            conflicts.append({"row": row, "type": "source_changed"})
        # Has someone else edited the translation since the export?
        if current_translation.updated_at > import_job.export_timestamp:
            conflicts.append({"row": row, "type": "translation_modified_externally"})
    return conflicts
```

Conflicts are shown in the preview. User can choose:
- **Skip conflicted rows** (default safe option)
- **Force overwrite** (admin only)

### Transactional commit + rollback

```python
def commit_import(import_job_id):
    job = db.fetch_one("SELECT * FROM import_jobs WHERE id = $1", import_job_id)
    
    with db.transaction():
        # Snapshot prior state for rollback
        applied_changes = []
        for row in job.rows:
            prior = db.fetch_one(
                "SELECT id, value, status, reviewer_action, reviewer_notes "
                "FROM translations WHERE id = $1", row.internal_id
            )
            applied_changes.append({
                "translation_id": row.internal_id,
                "prior": dict(prior),
            })
            apply_row_change(row)
        
        db.execute("""
            UPDATE import_jobs
            SET status = 'committed',
                committed_at = now(),
                rollback_expires_at = now() + interval '24 hours',
                applied_changes = $2
            WHERE id = $1
        """, import_job_id, json.dumps(applied_changes))

def rollback_import(import_job_id):
    job = db.fetch_one("SELECT * FROM import_jobs WHERE id = $1", import_job_id)
    if job.status != 'committed':
        raise Error("Cannot rollback: not committed")
    if now() > job.rollback_expires_at:
        raise Error("Rollback window expired")
    
    with db.transaction():
        for change in job.applied_changes:
            db.execute("""
                UPDATE translations
                SET value = $2, status = $3, reviewer_action = $4, reviewer_notes = $5
                WHERE id = $1
            """, change["translation_id"], change["prior"]["value"],
                 change["prior"]["status"], change["prior"]["reviewer_action"],
                 change["prior"]["reviewer_notes"])
        db.execute("UPDATE import_jobs SET status = 'rolled_back' WHERE id = $1",
                   import_job_id)
```

### Mapping `reviewer_action` to state changes

| `reviewer_action` value | What we do |
|---|---|
| `yes` | Set `value = mt_suggestion`, `status = approved`, `reviewer_action = accept`, `reviewed_at = now()` |
| `no` | Set `status = rejected`, `reviewer_action = reject`, `reviewed_at = now()`. Re-queue for MT. |
| `edit` | Set `value = edited_translation`, `status = approved`, `reviewer_action = edit`, `reviewed_at = now()`. Preserve `mt_value` untouched. |
| `needs_more_context` | Set `status = needs_more_context`, `reviewer_action = needs_more_context`, `reviewer_notes = notes`, `reviewed_at = now()` |
| (blank) | No change. Row skipped. |

Validation errors override the action: if `placeholders` don't match, force `status = needs_review` regardless.

## CLI usage

```bash
# Export
loc export --project clariti-web --locales fr-FR,de-DE --status needs_review \
  --output ./fr-de-review.xlsx

# Preview
loc import --file ./fr-de-review.xlsx --dry-run

# Commit
loc import --file ./fr-de-review.xlsx --commit

# Rollback
loc import --rollback <import_job_id>
```

## Schema versioning policy

- **v1** is the schema described above.
- Breaking changes (column added in middle, column removed, column renamed) → bump to v2.
- v1 importer remains supported for at least 6 months after v2 ships.
- The `_meta.schema_version` field is the only source of truth for which parser to use.

## Excel-specific traps to handle

1. **Leading zeros** — `001234` becomes `1234`. Force text format on all text columns.
2. **Long numbers in scientific notation** — `1234567890123` becomes `1.23E+12`. Same fix: text format.
3. **CSV-disguised XLSX** — reject; require true .xlsx files.
4. **Newlines in cells** — supported, but normalize `\r\n` to `\n` on import.
5. **Macros / VBA** — reject any file with macros. We only accept `.xlsx`, not `.xlsm`.
6. **Cells with leading/trailing whitespace** — strip on import unless source had it.
7. **Unicode normalization** — normalize to NFC on both export and import.
