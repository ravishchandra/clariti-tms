# 09 — Build Phases

Ordered for ease of build with Claude Code. Each phase plays to CC's strengths in sequence: schema DDL → Anthropic SDK → FastAPI CRUD → HTTP integrations → openpyxl → Next.js. The hard parts (Swift AST, Android layout XML deep grouping) are explicitly deferred to Phase 7.

Each phase produces something independently runnable. You can stop after any phase and have a usable system.

## Phase 1 — Foundation (week 1–2)

**Goal:** schema live, `loc init` works, can ingest a source file and see keys in DB.

**Why first:** Everything else depends on the schema. Pure SQL DDL + Docker Compose + one parser — CC can generate all of this in a single session. No external dependencies except Postgres.

- [ ] Monorepo scaffold: `app/` (FastAPI), `web/` (Next.js), `cli/`, `infra/`
- [ ] `docker compose up -d postgres && uvicorn app.main:app --reload` → running in one command
- [ ] Full schema from `04-data-model.md`: organizations, projects, repositories, component_contexts, locale_configs, keys, translations, translation_batches, glossary_terms, translation_memory, translation_history (trigger), mt_runs, import_jobs, screenshots, users
- [ ] Alembic migration for the full schema — one migration file
- [ ] Postgres trigger for `translation_history` — every translation change captured automatically
- [ ] Platform parsers (basic — key prefix grouping only; AST-based screen grouping is Phase 7):
  - iOS: `.strings` key=value parser, `.xcstrings` JSON parser, `.stringsdict` XML parser
  - Android: `strings.xml` parser, `translatable="false"` filter, `<plurals>` extraction
  - React: namespace JSON parser (flat + nested), ICU shape detection
- [ ] Placeholder extraction per platform: `%@`/`%1$@` (iOS), `%1$s`/`%2$d` (Android), `{{name}}` (i18next), `{name}` (ICU)
- [ ] Structural tag detection (`has_structural_tags`)
- [ ] Risk class heuristics (regex over source text)
- [ ] String type inference from key name pattern
- [ ] `loc init` — interactive scaffold for `tms.yml`
- [ ] `loc ingest-file <path> --repo <name>` — parse + upsert keys
- [ ] Seed script: one org, one project, two repos (ios + web), three locales, sample glossary
- [ ] CI: ruff + mypy + pytest for parser and validator unit tests

**Done = `loc ingest-file locales/en-US.json --repo frontend` populates keys in DB with correct grouping, placeholders, and risk classes.**

## Phase 2 — LLM Pipeline (weeks 2–3)

**Goal:** screen batches translate end-to-end, QA runs, cost is logged.

**Why second:** The LLM pipeline is the core value of the whole system. CC is building with the Anthropic SDK — its home turf. Validate the output quality before building any interface around it. This phase also produces the eval harness, which protects everything that comes after.

- [ ] `LLMProvider` Protocol + `AnthropicProvider` (Claude — primary)
- [ ] `OpenAIProvider` (fallback)
- [ ] `OllamaProvider` (local, no API key — contributors and offline dev)
- [ ] `DeepLProvider` (plain-text locales)
- [ ] Prompt template `translate_v1` (Jinja2 batch prompt from `05-llm-translation-pipeline.md`)
- [ ] Screen batch assembly: group draft keys by `(repository, component, screen, locale)`
- [ ] TM retrieval: HNSW index, batch embedding, platform-ranked
- [ ] Glossary: full project glossary in system prompt per batch
- [ ] Pre-processing: structural tag substitution before MT
- [ ] Post-processing: tag restoration + validator suite (placeholder, ICU, length, glossary)
- [ ] Back-translation QA (second LLM call, cosine similarity ≥ 0.80)
- [ ] Locale consistency eval (third LLM call, naturalness/consistency/accuracy 1–5)
- [ ] Risk-class routing: batch status after MT + QA
- [ ] `mt_runs` populated per batch call (full prompt + output + cost)
- [ ] Prompt caching for system prompt (Anthropic cache headers)
- [ ] Bootstrap sample export for new locales
- [ ] Eval harness: `loc eval --prompt translate_v2 --reference evals/fr-FR-reference.json`
- [ ] TMX export: `loc export-tm` / TMX import: `loc import-tm`
- [ ] `loc translate --project clariti-app --locale fr-FR`
- [ ] pgmq job queue for MT batches (replaces Redis — no new dependency)

**Done = ingest a real source file, run `loc translate`, inspect batch output. QA scores and cost logged. Eval harness runs against a reference set.**

## Phase 3 — REST API + CLI + SDKs (weeks 3–4)

**Goal:** every operation is accessible via API. CLI calls the API. Both SDKs generated.

**Why third:** FastAPI CRUD is CC's most exercised pattern. The OpenAPI spec is auto-generated by FastAPI — it's free. SDK generation from the spec is a single `make sdks` command. The CLI is Typer — easy. After this phase, the whole system is programmable.

- [ ] FastAPI router at `/api/v1/` with versioning middleware
- [ ] Auth: API key header (`X-API-Key`) for programmatic access, session cookie for web UI
- [ ] Full CRUD endpoints:
  - Organizations, projects, repositories, users
  - Keys: list (filter by status/locale/component), get, update
  - Translations: list, get, update value/status
  - Batches: list, get status, trigger MT, approve, reject
  - Glossary terms: CRUD
  - Locale configs: CRUD
  - Component contexts: CRUD
  - Export: trigger XLSX/TMX, poll status, download
  - Import: upload, preview, commit, rollback
  - Webhooks: GitHub receive, Contentful receive (endpoint stubs — wired in Phase 4)
- [ ] OpenAPI spec auto-generated at `/api/v1/openapi.json`
- [ ] TypeScript SDK: generated from OpenAPI spec (`@clariti-tms/sdk`, npm)
- [ ] Python SDK: generated from same spec (`clariti-tms`, PyPI)
- [ ] Generator config checked in; `make sdks` regenerates both
- [ ] `loc` CLI commands rewritten to call `/api/v1/` internally (no direct DB access from CLI)
- [ ] API key management: generate, list, revoke

**Done = `loc translate` calls the API. A CI script using the TypeScript SDK can drive ingest → translate → export. Both SDKs published.**

## Phase 4 — GitHub + Contentful + Platform Adapters (weeks 4–6)

**Goal:** full automated loop. Push code → MT runs → PR opens. No manual steps.

**Why fourth (before Excel):** GitHub + Contentful are HTTP calls and webhooks — the same pattern CC writes constantly. Moving this before Excel means you close the end-to-end loop sooner and test the system against real data before building the bulk review tooling. The platform parsers are also JSON/XML — straightforward for CC.

- [ ] `SourceAdapter` Protocol + `GitHubAdapter` (fetch + subscribe)
- [ ] GitHub App registration, webhook receiver with per-repository HMAC validation
- [ ] iOS parsers: `.xcstrings` (full Xcode 15 format), `.stringsdict`, key prefix screen grouping
- [ ] Android parsers: full `strings.xml` + `<plurals>`, HTML pre-processing, key prefix screen grouping
- [ ] React namespace parser: Trans component `<N>` tag detection, i18next suffix convention
- [ ] `PublicationAdapter` Protocol + `GitHubAdapter` publication implementation
- [ ] Platform writers:
  - iOS: `.strings` writer, `.xcstrings` writer, `.stringsdict` writer with CLDR categories
  - Android: `strings.xml` writer with full CLDR plural categories per locale
  - React: namespace JSON writer (preserve nesting, TypeScript key compatibility)
- [ ] `locale_file_path` + `serialize_locale_file` platform-aware helpers
- [ ] Publication service: scheduled every 15 minutes + on-demand via `POST /api/v1/repositories/{id}/publish`
- [ ] `ContentfulAdapter` (source + publication) — inbound webhook + outbound Management API
- [ ] Nightly reconciliation job (source vs DB diff, alert on drift)
- [ ] `loc add <key> <text>` — guided key addition
- [ ] `loc status [locale]` — coverage report
- [ ] `loc pull` — fetch approved translations to local repo
- [ ] CLA Assistant GitHub bot configured (required before accepting first external PR)

**Done = developer pushes a string → it appears in the review queue within 5 minutes → approving it opens a PR back to the repo. iOS, Android, React/TS, and Contentful all work end-to-end.**

## Phase 5 — Excel Round-Trip (weeks 6–7)

**Goal:** reviewer acts on translations offline in Excel; changes land in DB safely.

**Why fifth:** Now that the automated loop exists, Excel is the bridge to external reviewers and LSPs who won't use the web UI. CC knows openpyxl well. The validators and dry-run logic are pure Python — CC generates these quickly.

- [ ] XLSX export: one tab per locale, locked columns, dropdowns, color coding, `_meta` tab (see `07-excel-roundtrip.md`)
- [ ] Export includes hidden `_internal_id` (UUID) and `source_hash_at_export` columns (required for conflict detection)
- [ ] CLI: `loc export --project clariti-app --locales fr-FR,de-DE --status needs_review`
- [ ] HTTP: `POST /api/v1/exports` (async — poll for completion)
- [ ] XLSX import parser: schema version check, `_meta` integrity, column order validation
- [ ] Conflict detection: source changed since export, or translation modified externally since export
- [ ] Dry-run preview: counts by action, validation errors listed (see `07-excel-roundtrip.md` format)
- [ ] Import validators: placeholder match, length, glossary compliance, ICU plural parse, language detection
- [ ] Transactional commit with `import_jobs` audit row + 24h rollback window
- [ ] CLI: `loc import --file review.xlsx --dry-run` / `--commit` / `--rollback <job_id>`
- [ ] HTTP: `POST /api/v1/imports/preview`, `/commit`, `/rollback`
- [ ] Excel traps handled: leading zeros, scientific notation, `\r\n` normalization, NFC unicode, macro rejection

**Done = hand Excel to a reviewer → they act on it → import previews changes → commit → rollback works. 24h window verified.**

## Phase 6 — Web Review UI (weeks 7–9)

**Goal:** reviewers can clear a full queue keyboard-only in the browser.

**Why sixth:** By now the entire backend is complete and tested with real data. The web UI is a pure client of `/api/v1/` — no backend changes. Next.js + React is CC's strongest frontend surface. Building the UI last means you're building it on top of a fully working system, not designing it blind.

- [ ] Next.js + TypeScript, all data from `/api/v1/` (no direct DB access)
- [ ] Calibrate all UI against `DESIGN.md` — color tokens, typography, component rules, responsive breakpoints
- [ ] Auth: magic link email (NextAuth) or SSO — single sign-on option for teams
- [ ] Dashboard: queue surface (locales + screen counts + Start reviewing CTA) — not a stats page. See `06-human-review-workflow.md` dashboard spec.
- [ ] Screen-based review: all strings in a component in UX order
  - Aggregate QA scores + back-translation similarity per batch
  - Glossary hits and TM coverage shown per batch
  - Screenshot viewer (component context or per-key)
  - Source change diff when source changed since last approval
- [ ] Keyboard shortcuts: `A` approve screen, `j/k` nav, `e` edit, `r` reject, `f` flag, `Tab` focus, `Cmd+Enter` save, `?` help (see `06-human-review-workflow.md`)
- [ ] Batch actions: approve/reject/flag entire screen
- [ ] Individual string actions within a screen
- [ ] Glossary CRUD page, locale configs editor, component context editor
- [ ] Import/export pages: file upload, dry-run preview, commit, rollback status
- [ ] Key detail view: full history, MT run inspector, screenshots
- [ ] Locale bootstrap flow: export sample → review guide → mark bootstrapped
- [ ] Bulk actions: approve all in locale, approve by component, bulk assign reviewer

**Done = live walkthrough — reviewer clears a queue of 200 strings across 15 screens without touching a mouse.**

## Phase 7 — Extensions (post-MVP)

Build only after measuring real friction in the MVP. Ordered loosely by expected demand.

- [ ] **Swift AST screen grouping** — parse Swift source for `NSLocalizedString` calls, group by enclosing ViewController. Replaces key prefix inference for iOS.
- [ ] **Android layout XML screen grouping** — parse `res/layout/activity_*.xml` for `@string/` references, group by layout file. Replaces key prefix inference for Android.
- [ ] **XLIFF export/import** — for professional LSP exchange (`loc export-xliff`, `loc import-xliff`)
- [ ] **GitLab adapter** — community package (`clariti-tms-gitlab`); follows same SourceAdapter/PublicationAdapter pattern
- [ ] **Additional CMS adapters** — Sanity, Strapi, Prismic (community packages)
- [ ] **In-context Chrome extension** — Tolgee-style: translate strings while viewing staging. Overlay on live app, click string to see/edit translation.
- [ ] **OTA delivery for mobile** — CDN-fronted JSON endpoint, SDK checks for updates at app launch. Fixes typos without an App Store release.
- [ ] **Screenshot capture SDK** — web JS library: auto-screenshot when a string is visible on screen, attach to key record.
- [ ] **Slack notifications** — notify on stuck queues, bootstrap needed, MT errors
- [ ] **Analytics dashboard** — MT cost over time, edit rate per locale, quality score trends, glossary miss rate

## Timeline (with Claude Code)

Single engineer + CC: **7–8 weeks** for Phases 1–6.

CC compresses the boilerplate ceiling. The constraint is design and testing decisions, not typing speed.

## Milestones

- **End Phase 1:** `loc ingest-file` on a real repo → keys in DB, correctly grouped by screen.
- **End Phase 2:** `loc translate` on 100 strings × 5 locales → QA scores, cost tracked, eval harness green.
- **End Phase 3:** CI script using TypeScript SDK drives full ingest → translate → export flow.
- **End Phase 4:** Push a string → PR with translations opens automatically within 5 minutes.
- **End Phase 5:** Hand Excel to a reviewer → they act on it → import back → rollback works.
- **End Phase 6:** Live walkthrough — reviewer clears a screen queue keyboard-only.

## Definition of done for MVP

For one production project (one iOS repo + one React repo):

1. New keys pushed to main are picked up within 15 minutes.
2. MT runs per screen batch with validated output across all target locales.
3. High-risk strings require human review; auto-publish strings skip review.
4. Reviewers can act via web UI (screen-based) or Excel round-trip.
5. Approved translations are PR'd back to the repo within 15 minutes.
6. Full audit trail: who approved what, with which prompt version, QA scores included.
7. Bootstrap sample reviewed for each locale before it goes live.
