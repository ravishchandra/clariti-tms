Before you start

What you need.

A signed-in dashboard session, a project with a connected repository, and a few minutes when your reviewer is around. If any piece is missing, the guide tells you where to go and ships you back here.

The journey

Six steps, six clicks.

From here, every action lives inside the dashboard. After each action the UI tells you what to do next — no jumping into the CLI or GitHub to figure it out yourself.

STEP 01

Add the target locale.

Settings → Project → Target locales. Type a BCP-47 code (de-DE, pt-BR, ja-JP) and hit Add. The locale is appended to the project, a default locale-config row is created, and every existing key in the project gets a draft translation row for the new locale — all in one transaction.

Endpoint: POST /projects/{pid}/locale-configs?fan_out=true Returns: 200 {created: 247, already_existed: false}
STEP 02

Bootstrap the locale.

New locales need a native-speaker review of 50 sample strings before they can publish (this protects every batch that follows). Click Bootstrap walkthrough on the locale row in Settings → Locales; a four-step wizard takes care of the rest.

Pull 50 sample strings for your reviewer.

We'll generate an Excel file with your highest-risk strings first, capped at 50.

Resumable. Close the wizard while you wait for your reviewer; the locale row shows "de-DE · Bootstrapping · step 2 of 4 · Resume →" until the bootstrap completes. State persists on the locale config — multi-day reviewer turnarounds are fine.

Translate the queue.

STEP 05

Publish the approved batch to your repo.

Once a locale has approved batches, the Publish approved de-DE button appears on the review queue header. One click opens a pull request against your GitHub repo — translated values committed into lib/l10n/app_de_DE.arb, schema preserved, @key metadata round-tripped verbatim.

→ owner/clariti-app
PR #42 opened against owner/clariti-app Open PR ↗
The result strip persists. Unlike a toast, the PR link stays visible until the next batch transitions or you navigate away. Hit it days later, you'll still find it.
Endpoint: POST /publications/repositories/{rid}/publish?locale=de-DE Timeout: 30s client-side; "Still running" fallback. Server is durable.
STEP 06

Merge the PR.

On GitHub, your team reviews and merges the PR like any other code change. ClaritiTMS marks the published translations as published on the next webhook ping. That's the round-trip — your source repo is now multi-lingual.

✓ 2 reviewers approved · ready to merge
When things go sideways

What you'll see when something fails.

Every step has a named error path with copy that tells you exactly what to do next. No raw stack traces, no "contact support" dead-ends.

Add locale

Locale already on this project.

Returns 200 + already_existed: true — no scary 409. The dialog closes quietly and the locale row jumps into focus with a fresh highlight, so you can edit it directly in Locales.

Ingest

Wrong file format.

Client-side guard before the upload leaves the browser. "This repo expects .arb files. Upload app_en.arb, or change file_format in repo settings." Inline link to the settings tab.

Bulk MT

Some batches failed.

Inline strip shows "43 queued · 4 failed." The retry button only re-issues failures. Rate-limit failures wait the LLM provider's Retry-After automatically.

Publish

GitHub App access expired.

Inline card: "GitHub access expired. Reconnect in Settings → Repositories." The Repositories row flips into a sticky red badge until the next successful publish.

Publish

A PR for this locale is already open.

No duplicate PR. The result strip shows "A PR for de-DE is already open: PR #41 [Open]" — merge or close that one first, then publish again.

Bootstrap

The uploaded reply doesn't match the locale.

The dry-run preview validates that the file's locale matches the wizard's target. If you uploaded the French file into the German wizard, commit is blocked: "This file isn't for de-DE."

Frequently asked

Three things people ask first.

FAQ 01

Can I do this from the CLI instead?

Yes — every step in this guide has a 1:1 CLI command. loc init, loc ingest-file, loc translate, loc publish. Use whichever surface fits your workflow. Agents (Claude Code, Cursor, Cline) can drive the same flow through the MCP server.

FAQ 02

What if I don't have a GitHub App connected?

Steps 1–4 work without it. Step 5 (publish) will fail until a GitHub App is installed and its installation id is pasted into the repository settings. The dashboard surfaces the "install the App" link inline; once installed and the id is set, the Publish button activates.

FAQ 03

Why do I have to bootstrap?

Because nobody on your team speaks every language. Bootstrap is a one-time native-speaker pass on 50 high-risk strings — they become the prompt-tuning seed for the rest of the locale. Skipping bootstrap is a footgun; docs/06 explains the policy in detail.
